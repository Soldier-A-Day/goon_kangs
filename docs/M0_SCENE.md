# M0 성능 게이트 — 측정 씬 구성

문서번호 SAD-M0-001 · 근거: `SAD-GDD-001` 18.0·19.0 · `SAD-ART-001`(ASSETS.md) §0·§9·§11

---

## 0. 이 문서가 푸는 문제

기획서 19.0은 M0의 Unity 트랙을 이렇게 규정한다.

> M0의 Unity 트랙은 **게임을 만드는 것이 아니라 숫자를 재는 것**이 목적이다.

그런데 ASSETS.md §11의 M0 에셋 범위는 이렇다.

> 캐릭터 베이스 1 + 피복 1세트, 야외 맵 1, 온도 파티클 1밴드

**이 둘을 그대로 합치면 측정이 무의미해진다.** M0 에셋만 배치한 씬은 실제 최대 부하의
1/4에도 못 미치기 때문이다. 거기서 60fps가 나와도 완성된 게임이 60fps라는 근거가 되지 못한다.

| | 폴리 | 최대 부하 대비 |
|---|---:|---:|
| M0 에셋 범위 그대로 | 약 **105,000** | 24% |
| 실제 최대 부하 (§9) | **436,000** | 100% |

그래서 M0 씬은 **두 개**여야 한다.

1. `M0_Synthetic` — 프록시 지오메트리로 목표 부하를 **합성**한다. 실제 에셋 없이 같은
   폴리·드로우콜·파티클 부하를 만든다. 이게 진짜 게이트다
2. `M0_Real` — M0 에셋만 배치한다. 실제 에셋의 렌더 특성(스킨드 메시, 반투명, 그림자)이
   프록시와 다르게 굴지 않는지 대조한다

합성 씬이 통과하고 실측 씬이 그보다 무겁게 나오면, 차이나는 부분이 곧 병목이다.

## 1. 목표 부하 — 무엇을 재현해야 하나

ASSETS.md §9 "동시 표시 합계 (최대 부하)" 436,000 tris를 분해한 것이다.

| 구성 | 실제 기여 | M0 재현 방법 |
|---|---:|---|
| 캐릭터 4인 + 피복 | 62,000 | **실제 에셋** (M0 범위에 있다) |
| 간부 NPC 3 + 배경 병력 2 | 16,000 | 프록시 — 스킨드 메시 5체 |
| 부대 상시 맵 | 120,000 | 야외 맵 1개(실제) + 프록시 보충 |
| 훈련 맵 1개 로드 | 200,000 | 프록시 — 행군 코스 구간 기준 |
| 상호작용 소품 | 30,000 | 프록시 — GPU 인스턴싱 20종 |
| 지급 장비 | 8,000 | **실제 에셋** (소총·무전기) |
| **합계** | **436,000** | |

> 부대 맵과 훈련 맵이 실제로 동시에 보이지는 않는다. 그래도 둘을 더하는 이유는
> **전환 구간에서 양쪽이 메모리에 함께 있기 때문**이며, 힙 측정의 최악 지점이 거기다.

## 2. 진짜 병목은 폴리가 아니라 드로우콜이다

ASSETS.md §0이 못박는다.

> WebGL2는 폴리보다 **드로우콜이 병목**. 정적 배칭 + GPU 인스턴싱 필수

폴리는 436K / 700K = **62%**로 여유가 있다. 드로우콜을 따로 세어야 한다.

| 구성 | 드로우콜 | 근거 |
|---|---:|---|
| 캐릭터 4인 | **28** | 스킨드 메시는 정적 배칭 불가. 베이스 1 + 피복 6슬롯 = 7/인 |
| NPC 5체 | 10 | 피복 병합 가정, 2/체 |
| 환경 (정적 배칭 후) | 40~80 | **재질 수가 곧 드로우콜.** 아틀라스 통합 정도에 좌우된다 |
| 소품 (GPU 인스턴싱) | 20 | 화면에 보이는 종류당 1 |
| 파티클 8종 | 16 | 종당 1~2 |
| 소계 | **114~154** | |
| **× 그림자 패스** | **228~308** | 실시간 광원 1개 → 캐스터를 한 번 더 그린다 |
| UI 캔버스 | 20 | |
| **합계** | **약 250~330** | 목표 800 대비 **31~41%** |

수치상 여유는 있지만 **두 곳에서 급증한다.**

- **배칭 실패** — 재질이 쪼개지거나 동적 오브젝트가 늘면 환경 드로우콜이 3~4배로 뛴다
- **그림자 캐스케이드** — 캐스케이드를 2단 이상 쓰면 캐스터 패스가 그만큼 반복된다

M0에서 **이 두 값을 일부러 나쁘게 만들어 상한을 확인**해야 한다. 잘 나온 숫자 하나보다
"어디서부터 무너지는가"가 M0의 산출물이다.

## 3. 씬 A — `M0_Synthetic` (게이트)

프록시로 목표 부하를 합성한다. 실제 에셋 제작을 기다리지 않는다.

### 3.1 배치

| 오브젝트 | 수량 | 개당 폴리 | 소계 | 렌더 특성 |
|---|---:|---:|---:|---|
| 스킨드 프록시 (캐릭터 대역) | 9 | 15,500 | 139,500 | SkinnedMeshRenderer + 애니메이터 |
| 환경 블록 (정적) | 240 | 500 | 120,000 | 정적 배칭 대상, 재질 8종 |
| 훈련 맵 프록시 (정적) | 200 | 1,000 | 200,000 | 오클루전 컬링 대상 |
| 소품 인스턴스 | 20종 × 5 | 300 | 30,000 | GPU 인스턴싱 |
| **합계** | | | **489,500** | 목표 436K 대비 +12% 여유 |

폴리를 목표보다 조금 높게 잡는다 — 통과 판정에 마진을 남기기 위해서다.

### 3.2 함께 켜는 것

- **파티클 1밴드** — 극혹한 기준. 서리·눈 800 + 입김 40 × 4인 = 960 파티클
- **URP Volume 1개** — 청록 그레이딩 + 비네트. 후처리가 프레임에 미치는 몫을 본다
- **실시간 그림자 1광원** — 태양. 나머지는 베이크로 가정하고 끈다

### 3.3 부하 스윕

한 번 재고 끝내지 않는다. 아래를 단계적으로 올리며 **무너지는 지점**을 찾는다.

| 축 | 시작 | 증가 | 관심사 |
|---|---|---|---|
| 환경 재질 수 | 8종 | 8 → 16 → 32 | 배칭이 언제 깨지나 |
| 그림자 캐스케이드 | 1단 | 1 → 2 → 4 | 캐스터 패스 비용 |
| 파티클 총량 | 960 | ×2 → ×4 | 축소 순위 1번의 실제 여유 |
| 동시 캐릭터 | 4 | 4 → 6 → 8 | 4인이 정말 상한인지 |

## 4. 씬 B — `M0_Real` (대조)

M0 에셋 범위만 배치한다. 프록시와 실제 에셋의 렌더 특성 차이를 잡기 위한 것이다.

| 구성 | 폴리 |
|---|---:|
| 캐릭터 베이스 1 + 피복 1세트 × 4인 | 62,000 |
| 야외 맵 1 (연병장 40,000 + 외곽 일부) | 약 60,000 |
| 지급 장비 (소총 4정) | 12,000 |
| **합계** | **약 134,000** |

여기서 60fps가 나오는 것은 **당연하다.** 이 씬의 목적은 통과가 아니라,
같은 폴리에서 합성 씬보다 무겁게 나오는 항목을 찾는 것이다. 스킨드 메시의 본 수,
반투명 재질, 그림자 캐스팅 설정이 후보다.

## 5. 100분 힙 측정 — 시간이 아니라 반복이 쌓인다

기획서 표 18-2의 "100분 세션 힙 안정성 · 누수 0 · **완화 불가**"를 재는 방법이다.

누수는 시간이 아니라 **반복 횟수**에 비례한다. 100분 세션에서 실제로 반복되는 것은 이것들이다.

| 반복 | 100분당 횟수 | 계산 근거 |
|---|---:|---|
| 스냅샷 파싱 | **60,000** | 10Hz × 6,000초 (17.0 NET-01) |
| 시간대 전환 | **108** | 18일 × 6칸 (4.0) |
| 훈련 맵 로드/언로드 | 9 | 훈련 9종 (표 9-1) |
| 온도 밴드 전환 | 18 | 하루 1회 기온 롤 (5.0) |
| UI 열고 닫기 | 수백 | 수첩·하달 창·지도 |

**스냅샷 파싱 60,000회가 압도적이다.** `JsonUtility.FromJson`이 매번 객체를 새로 만들면
GC 압력이 그대로 누적된다. M0에서 여기부터 본다.

### 측정 절차

1. 게임서버를 띄우고 더미 4인을 WS로 접속시킨다 (`services/gameserver`)
2. `M0_Synthetic`을 WebGL로 빌드해 브라우저에서 100분 연속 구동
3. Unity Profiler(원격) + 브라우저 `performance.memory`를 동시에 기록
4. 10분 간격으로 GC 후 힙 저점을 기록 — **저점이 우상향하면 누수**다

> 시간을 줄여 재는 것은 의미가 없다. 반복 횟수가 줄면 누수도 같이 줄어 안 보인다.
> 다만 스냅샷 주기를 10Hz → 100Hz로 올려 **60,000회를 10분에 소화**하는 것은 유효한 단축이다.

## 6. 판정과 미달 시 대응

| 항목 | 목표 | 완화 |
|---|---|---|
| 4인 야외 프레임 | 60fps / 최저 30 | **불가** |
| 100분 힙 | 누수 0 | **불가** |
| 초기 다운로드 | ≤ 120MB | 가능 |
| 콜드 스타트 | ≤ 90초 | 가능 |

미달 시 배포 타깃을 바꾸지 않는다. **스코프를 깎되 순서가 정해져 있다**(19.0).

| 순위 | 깎는 것 | 이 문서에서 대응하는 지점 |
|---:|---|---|
| 1 | 파티클 예산 · 후처리 단계 | §3.2 파티클 960 → 축소, Volume 단계 축소 |
| 2 | 야외 맵 축소 · 시야 거리 단축 | §3.1 훈련 맵 프록시 200,000 → 축소 |
| 3 | 배경 NPC 제거 | §1 NPC 16,000 제거 |
| 4 | 4인 → 3인 + NPC (**최후 수단**) | §3.3 동시 캐릭터 스윕이 이 판단의 근거가 된다 |

순위를 미리 정해둔 이유는 기획서가 적은 그대로다 — 성능 문제가 터진 뒤에 급하게 정하면
가장 깎기 쉬운 것(인원)부터 깎게 되고, 4보직 1:1 대응에서 인원을 줄이면 곧 보직이 사라진다.

## 6.5 실측 기록

### 1차 (2026-07-31, Apple M2 · Chrome · WebGL2 · 1920×1200)

프록시 합성 부하 기준.

| 배율 | 오브젝트 | 삼각형 | fps |
|---|---:|---:|---:|
| 1/32 | 34 | 31,000 | 60.0 |
| 1/16 | 48 | 41,000 | 60.0 |
| 1/8 | 76 | 61,500 | 60.0 |
| 1/4 | 132 | 117,000 | 60.0 |
| 1/2 | 264 | 234,000 | 60.0 |
| **1/1 (목표)** | **549** | **489,500** | **60.0** |

**목표 부하에서 60fps.** 다만 전 구간이 정확히 60.0이므로 이는 **vsync 상한**이지 여유의 측정이 아니다.
34개에서도 60, 549개에서도 60이면 61fps가 한계인지 300fps가 한계인지 구분되지 않는다.
그래서 스윕을 목표의 8배까지 연장해 **실제로 깨지는 지점**을 찾는다.

> 프록시에 없는 것: 스킨드 메시, 텍스처·노멀맵, 파티클 8종, URP Volume 후처리.
> 60fps는 **필요조건이지 충분조건이 아니다.**

### 2차 (2026-07-31) — 스킨드·파티클·후처리를 켜고 8배까지

1차가 재지 못한 축을 `HeavyAxes`로 붙였다. 스킨드는 본 30개 체인을 실제로 달고
매 프레임 흔들어 **스키닝이 진짜 돌게** 했다 — 본 없이 `SkinnedMeshRenderer`만
붙이면 드로우콜만 재고 CPU 스키닝 비용을 놓친다.

| 배율 | 오브젝트 | 삼각형 | 스킨드 | 파티클 | fps |
|---|---:|---:|---:|---:|---:|
| 1/32 | 36 | 47,000 | 1 | 30 | 60.0 |
| 1/16 | 49 | 56,500 | 1 | 60 | 60.0 |
| 1/8 | 77 | 77,000 | 1 | 120 | 60.0 |
| 1/4 | 134 | 148,000 | 2 | 240 | 60.0 |
| 1/2 | 268 | 296,000 | 4 | 480 | 60.0 |
| **1/1 (목표)** | **558** | **629,000** | **9** | **960** | **59.0** |
| 2배 | 1,116 | 1,258,000 | 18 | 1,920 | 60.0 |
| 4배 | 2,232 | 2,516,000 | 36 | 3,840 | 60.0 |
| 8배 | 4,464 | 5,032,000 | 72 | 7,680 | 59.2 |

**결론: 폴리·오브젝트·스킨드·파티클·후처리 — 이 다섯 축은 병목이 아니다.**
목표의 8배(삼각형 8배, 스킨드 8배, 파티클 8배를 동시에)에서도 59.2fps다.

목표 59.0과 8배 59.2는 **부하 응답이 아니다.** 부하가 8배 늘었는데 fps가 올라갔다면
그건 측정 노이즈(생성 직후 GC·파티클 워밍업)이지 신호가 아니다.

#### 이 표가 말하지 않는 것

| | |
|---|---|
| **여유의 크기** | 60fps는 vsync 상한이다. 8배에서 60이면 여유가 8배 이상이라는 것만 알 수 있고, 그게 10배인지 50배인지는 모른다. 알 필요도 없다 — 8배면 판정에 충분하다 |
| **최저 사양** | **Apple M2 / 24GB에서 잰 값이다.** 표 18-2의 최저 사양 기기가 아니다. 이 결과는 "이 축들이 M2에서 여유롭다"이지 "모든 대상 기기에서 통과"가 아니다. 최저 사양 실측은 남아 있다 |
| **텍스처 메모리** | 프록시는 재질 8종을 쓰지만 전부 단색이다. 2K 알베도+노멀 20세트가 올라가면 VRAM과 초기 로딩이 달라진다. fps와 별개 축이다 |
| **100분 힙** | 표 18-2의 다른 **완화 불가** 항목. 3초 측정으로는 원리적으로 알 수 없다 (§5) |

드로우콜 우려(ASSETS.md §0)는 여기서 해소됐다. 8배에서 스킨드 72체 = 배칭 불가
드로우콜 72개인데 프레임이 멀쩡하다. 실제 게임은 9체다.

### 3차 (2026-07-31) — 100분 힙, 30분 시점 중간 결과

`?mode=heap` — 목표 부하 고정 + 10Hz 스냅샷 파싱.

| 분 | 힙 저점 | 최악 프레임 | 평균 프레임 |
|---:|---:|---:|---:|
| 0 | 1.8MB | 2041ms | 23.8ms |
| 10 | 2.8MB | 1051ms | 26.0ms |
| 20 | 2.8MB | 221ms | 25.2ms |
| 30 | 2.9MB | 385ms | 26.4ms |

**힙: 통과.** 판정은 `_buckets[1]`(0번은 로딩분이 섞여 버린다)과 마지막의 차이로 한다 —
**2.8 → 2.9MB, +0.1MB.** 스냅샷 1.8만 회를 파싱하고도 저점이 평평하다.

**프레임: 이 표의 값은 무효다.** 평균 25ms(40fps)인데 같은 부하를 2차 스윕에서
쟀을 때는 59.0fps였다. 부하는 같고 달라진 건 오버레이뿐이다.

원인은 `HeapProbe.OnGUI`였다. 표를 띄우면서 **매 이벤트마다**(OnGUI는 프레임당
Layout·Repaint 둘 이상 불린다) `Report()`로 StringBuilder를 새로 만들고,
`GetComponent`를 돌리고, `Profiler.GetMonoUsedSizeLong()`을 호출했다.

세 번째가 특히 나쁘다 — **계측기가 자기가 재는 힙에 할당을 쏟는다.** 저점이
평평하게 나온 건 그 할당이 전부 회수됐기 때문이지 구조가 옳아서가 아니다.

`AutoSweep`에 적어둔 원칙(*도구가 성능에 의존하면 안 된다*)을 `HeapProbe`에서
그대로 어겼다. 고친 뒤: 오버레이 문자열은 0.5초마다 한 번만 조립하고, 힙 값은
Update가 이미 뜬 표본을 재사용하고, `OnGUI`는 Repaint 이벤트에서만 그린다.

최악 프레임 2041/1051/221/385ms는 오버레이로 설명되지 않는다. 0분의 2041ms는
씬 생성(549 오브젝트 + 본 리그 9체)이라 예상된 값이고, 나머지는 Mono 힙이
2.8MB뿐이라 GC일 수 없다 — 창 포커스가 빠진 흔적으로 본다.

### 4차 (2026-07-31) — 가속 힙 측정, **두 게이트 모두 통과**

`?mode=heap&hz=100&bucket=60` — 목표 부하 고정 + 100Hz 스냅샷 파싱.
**14분 × 100Hz = 8.4만 회.** 100분 세션 한 판(6만 회)을 넘겼다.

| 분 | 힙 저점 | 최악 프레임 | 평균 |
|---:|---:|---:|---:|
| 0 | 1.2MB | *무효 (씬 생성)* | — |
| 1 | 2.1MB | 18.0ms | 16.7ms |
| 2 | 2.0MB | 18.0ms | 16.7ms |
| 3 | 2.1MB | 18.0ms | 16.7ms |
| 4 | 2.2MB | 18.0ms | 16.7ms |
| 5–9 | 2.0–2.1MB | 19.0ms | 16.7ms |
| 10 | 2.2MB | 19.0ms | 16.7ms |
| 11 | 2.1MB | 19.0ms | 16.7ms |
| 12 | 2.3MB | 19.0ms | 16.7ms |
| 13 | 2.1MB | 19.0ms | 16.7ms |
| 14 | 2.3MB | 19.0ms | 16.7ms |

| 게이트 | 목표 | 실측 | |
|---|---|---|---|
| 4인 야외 프레임 | 60fps / 최저 30 | 평균 16.7ms · **최악 19ms** | 통과 |
| 100분 힙 | 누수 0 | 저점 2.1 → 2.3MB (**+0.2MB**) | 통과 |

힙 저점은 2.0~2.3에서 오르내릴 뿐 **추세가 없다.** 8.4만 회를 파싱하고도
1MB도 늘지 않았으므로 `JsonUtility.FromJson` 경로에 참조를 붙드는 곳이 없다.

프레임은 평균 16.7ms — 정확히 vsync 60fps다. 최악 19ms는 한 프레임이 한 번
튄 정도이고, **최악조차 기준선(33.3ms)의 절반을 조금 넘는 수준**이다.
1~3차에서 프레임을 못 믿었던 이유(계측기 오염·포커스 손실)가 둘 다 제거되어
이 값이 처음으로 판정에 쓸 수 있는 값이다.

#### 이 결과가 덮지 않는 것

| | |
|---|---|
| **관리 힙만 쟀다** | `Profiler.GetMonoUsedSizeLong()`은 C# 힙이다. 파싱 누수가 나타날 자리는 맞지만, WASM 힙(1GB 설정)·텍스처·메시 등 네이티브 쪽은 다른 축이다 |
| **최저 사양** | Apple M2에서 잰 값이다. 누수 유무는 기기와 무관하지만 프레임은 아니다 |
| **프록시 자산** | 단색 재질 8종이다. 2K 알베도+노멀 20세트가 올라가면 VRAM과 콜드 스타트가 달라진다 |

#### 가속 측정

§5에 적어둔 유효한 단축을 구현했다. `?mode=heap&hz=100&bucket=60` 이면
**6만 회를 10분에** 소화한다. 누수는 시간이 아니라 반복 횟수에 비례하므로
이 치환은 성립한다 — 반대로 시간만 줄이는 것은 무효다.

100Hz를 내려면 프레임당 여러 건을 파싱해야 한다. 프레임당 한 건이면 **fps가 상한**이
되어 60fps에서는 100Hz를 요청해도 60Hz밖에 나오지 않는다.

### 측정할 때 걸린 것들

에디터에서는 보이지 않고 빌드에서만 터진 것들이다. 실제 에셋이 올라간 뒤 만났으면
원인 찾기가 훨씬 어려웠을 것이므로, M0을 먼저 하는 값어치가 여기 있다.

| 증상 | 원인 |
|---|---|
| **컴포넌트를 추가했는데 씬에 없다** | `BuildWebGL`이 씬 파일이 없을 때만 `CreateScene`을 불렀다. 코드는 빌드에 들어가니 컴파일도 통하고 에러도 없다 — 붙일 오브젝트가 없을 뿐이다. 씬은 전부 코드 생성이므로 **매번 다시 만든다** |
| 검은 화면 · 메시지 없는 예외 | `Shader.Find`가 빌드에서 null. 문자열 조회는 참조로 잡히지 않아 셰이더가 빌드에서 빠진다 |
| 빌드 16분 초과 | Always Included Shaders에 URP Lit → **전 변형** 컴파일. 머티리얼 에셋을 씬이 참조하게 하면 쓰이는 변형만 들어간다 |
| 전부 마젠타 | URP **파이프라인 미지정**. 패키지를 넣는 것과 파이프라인을 지정하는 것은 별개다 |
| 정적 배칭 조용히 실패 | `UploadMeshData(markNoLongerReadable: true)` — 읽을 수 없는 메시는 배칭되지 않는다 |
| 재빌드해도 옛 빌드가 돎 | Unity가 빌드를 **IndexedDB에 캐시**한다. 서버의 `no-store`로는 막을 수 없다 |
| **fps가 항상 1.0** | 브라우저 창이 가려지면 Chrome이 rAF를 **1fps로 스로틀**한다. Unity WebGL 메인 루프가 rAF라 그대로 따라간다. **측정 시 창이 보이는 상태여야 한다** |

마지막 항목이 특히 위험하다. 부하와 무관하게 항상 1.0이 나오므로 성능 문제로 오인하기 쉽다 —
**부하를 32분의 1로 줄여도 1.0이면 그건 스로틀이지 성능이 아니다.**

### 도구가 성능에 의존하면 안 된다

처음에는 키 입력으로 스윕하려 했으나 성립하지 않았다. 입력은 프레임당 한 번 폴링되므로
**fps가 낮을수록 조작이 안 먹는다.** 성능이 나쁠 때 성능을 조사하는 도구가 성능에 의존하면
정작 필요한 순간에 쓸 수 없다. `AutoSweep`이 스스로 도는 이유다.
