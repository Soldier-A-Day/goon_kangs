# M0 성능 게이트 — 측정 씬 구성

문서번호 SAD-M0-001 · 근거: `SAD-GDD-001` 18.0·19.0 · `SAD-ART-001`(ASSETS.md) §0·§9·§11

---

## 0. 이 문서가 푸는 문제

기획서 19.0은 M0의 Unity 트랙을 이렇게 규정한다.

> M0의 Unity 트랙은 **게임을 만드는 것이 아니라 숫자를 재는 것**이 목적이다.

그런데 ASSETS.md §11의 M0 에셋 범위는 이렇다.

> 캐릭터 베이스 1 + 피복 1세트, 야외 맵 1, 온도 파티클 1밴드

**이 둘을 그대로 합치면 측정이 무의미해진다.** M0 에셋만 배치한 씬은 실제 최대 부하의
1/4에도 못 미치기 때문이다. 거기서 60fps가 나와도 완성된 게임이 60fps라는 근거가 되지 못한다.

| | 폴리 | 최대 부하 대비 |
|---|---:|---:|
| M0 에셋 범위 그대로 | 약 **105,000** | 24% |
| 실제 최대 부하 (§9) | **436,000** | 100% |

그래서 M0 씬은 **두 개**여야 한다.

1. `M0_Synthetic` — 프록시 지오메트리로 목표 부하를 **합성**한다. 실제 에셋 없이 같은
   폴리·드로우콜·파티클 부하를 만든다. 이게 진짜 게이트다
2. `M0_Real` — M0 에셋만 배치한다. 실제 에셋의 렌더 특성(스킨드 메시, 반투명, 그림자)이
   프록시와 다르게 굴지 않는지 대조한다

합성 씬이 통과하고 실측 씬이 그보다 무겁게 나오면, 차이나는 부분이 곧 병목이다.

---

## 1. 목표 부하 — 무엇을 재현해야 하나

ASSETS.md §9 "동시 표시 합계 (최대 부하)" 436,000 tris를 분해한 것이다.

| 구성 | 실제 기여 | M0 재현 방법 |
|---|---:|---|
| 캐릭터 4인 + 피복 | 62,000 | **실제 에셋** (M0 범위에 있다) |
| 간부 NPC 3 + 배경 병력 2 | 16,000 | 프록시 — 스킨드 메시 5체 |
| 부대 상시 맵 | 120,000 | 야외 맵 1개(실제) + 프록시 보충 |
| 훈련 맵 1개 로드 | 200,000 | 프록시 — 행군 코스 구간 기준 |
| 상호작용 소품 | 30,000 | 프록시 — GPU 인스턴싱 20종 |
| 지급 장비 | 8,000 | **실제 에셋** (소총·무전기) |
| **합계** | **436,000** | |

> 부대 맵과 훈련 맵이 실제로 동시에 보이지는 않는다. 그래도 둘을 더하는 이유는
> **전환 구간에서 양쪽이 메모리에 함께 있기 때문**이며, 힙 측정의 최악 지점이 거기다.

## 2. 진짜 병목은 폴리가 아니라 드로우콜이다

ASSETS.md §0이 못박는다.

> WebGL2는 폴리보다 **드로우콜이 병목**. 정적 배칭 + GPU 인스턴싱 필수

폴리는 436K / 700K = **62%**로 여유가 있다. 드로우콜을 따로 세어야 한다.

| 구성 | 드로우콜 | 근거 |
|---|---:|---|
| 캐릭터 4인 | **28** | 스킨드 메시는 정적 배칭 불가. 베이스 1 + 피복 6슬롯 = 7/인 |
| NPC 5체 | 10 | 피복 병합 가정, 2/체 |
| 환경 (정적 배칭 후) | 40~80 | **재질 수가 곧 드로우콜.** 아틀라스 통합 정도에 좌우된다 |
| 소품 (GPU 인스턴싱) | 20 | 화면에 보이는 종류당 1 |
| 파티클 8종 | 16 | 종당 1~2 |
| 소계 | **114~154** | |
| **× 그림자 패스** | **228~308** | 실시간 광원 1개 → 캐스터를 한 번 더 그린다 |
| UI 캔버스 | 20 | |
| **합계** | **약 250~330** | 목표 800 대비 **31~41%** |

수치상 여유는 있지만 **두 곳에서 급증한다.**

- **배칭 실패** — 재질이 쪼개지거나 동적 오브젝트가 늘면 환경 드로우콜이 3~4배로 뛴다
- **그림자 캐스케이드** — 캐스케이드를 2단 이상 쓰면 캐스터 패스가 그만큼 반복된다

M0에서 **이 두 값을 일부러 나쁘게 만들어 상한을 확인**해야 한다. 잘 나온 숫자 하나보다
"어디서부터 무너지는가"가 M0의 산출물이다.

## 3. 씬 A — `M0_Synthetic` (게이트)

프록시로 목표 부하를 합성한다. 실제 에셋 제작을 기다리지 않는다.

### 3.1 배치

| 오브젝트 | 수량 | 개당 폴리 | 소계 | 렌더 특성 |
|---|---:|---:|---:|---|
| 스킨드 프록시 (캐릭터 대역) | 9 | 15,500 | 139,500 | SkinnedMeshRenderer + 애니메이터 |
| 환경 블록 (정적) | 240 | 500 | 120,000 | 정적 배칭 대상, 재질 8종 |
| 훈련 맵 프록시 (정적) | 200 | 1,000 | 200,000 | 오클루전 컬링 대상 |
| 소품 인스턴스 | 20종 × 5 | 300 | 30,000 | GPU 인스턴싱 |
| **합계** | | | **489,500** | 목표 436K 대비 +12% 여유 |

폴리를 목표보다 조금 높게 잡는다 — 통과 판정에 마진을 남기기 위해서다.

### 3.2 함께 켜는 것

- **파티클 1밴드** — 극혹한 기준. 서리·눈 800 + 입김 40 × 4인 = 960 파티클
- **URP Volume 1개** — 청록 그레이딩 + 비네트. 후처리가 프레임에 미치는 몫을 본다
- **실시간 그림자 1광원** — 태양. 나머지는 베이크로 가정하고 끈다

### 3.3 부하 스윕

한 번 재고 끝내지 않는다. 아래를 단계적으로 올리며 **무너지는 지점**을 찾는다.

| 축 | 시작 | 증가 | 관심사 |
|---|---|---|---|
| 환경 재질 수 | 8종 | 8 → 16 → 32 | 배칭이 언제 깨지나 |
| 그림자 캐스케이드 | 1단 | 1 → 2 → 4 | 캐스터 패스 비용 |
| 파티클 총량 | 960 | ×2 → ×4 | 축소 순위 1번의 실제 여유 |
| 동시 캐릭터 | 4 | 4 → 6 → 8 | 4인이 정말 상한인지 |

## 4. 씬 B — `M0_Real` (대조)

M0 에셋 범위만 배치한다. 프록시와 실제 에셋의 렌더 특성 차이를 잡기 위한 것이다.

| 구성 | 폴리 |
|---|---:|
| 캐릭터 베이스 1 + 피복 1세트 × 4인 | 62,000 |
| 야외 맵 1 (연병장 40,000 + 외곽 일부) | 약 60,000 |
| 지급 장비 (소총 4정) | 12,000 |
| **합계** | **약 134,000** |

여기서 60fps가 나오는 것은 **당연하다.** 이 씬의 목적은 통과가 아니라,
같은 폴리에서 합성 씬보다 무겁게 나오는 항목을 찾는 것이다. 스킨드 메시의 본 수,
반투명 재질, 그림자 캐스팅 설정이 후보다.

## 5. 100분 힙 측정 — 시간이 아니라 반복이 쌓인다

기획서 표 18-2의 "100분 세션 힙 안정성 · 누수 0 · **완화 불가**"를 재는 방법이다.

누수는 시간이 아니라 **반복 횟수**에 비례한다. 100분 세션에서 실제로 반복되는 것은 이것들이다.

| 반복 | 100분당 횟수 | 계산 근거 |
|---|---:|---|
| 스냅샷 파싱 | **60,000** | 10Hz × 6,000초 (17.0 NET-01) |
| 시간대 전환 | **108** | 18일 × 6칸 (4.0) |
| 훈련 맵 로드/언로드 | 9 | 훈련 9종 (표 9-1) |
| 온도 밴드 전환 | 18 | 하루 1회 기온 롤 (5.0) |
| UI 열고 닫기 | 수백 | 수첩·하달 창·지도 |

**스냅샷 파싱 60,000회가 압도적이다.** `JsonUtility.FromJson`이 매번 객체를 새로 만들면
GC 압력이 그대로 누적된다. M0에서 여기부터 본다.

### 측정 절차

1. 게임서버를 띄우고 더미 4인을 WS로 접속시킨다 (`services/gameserver`)
2. `M0_Synthetic`을 WebGL로 빌드해 브라우저에서 100분 연속 구동
3. Unity Profiler(원격) + 브라우저 `performance.memory`를 동시에 기록
4. 10분 간격으로 GC 후 힙 저점을 기록 — **저점이 우상향하면 누수**다

> 시간을 줄여 재는 것은 의미가 없다. 반복 횟수가 줄면 누수도 같이 줄어 안 보인다.
> 다만 스냅샷 주기를 10Hz → 100Hz로 올려 **60,000회를 10분에 소화**하는 것은 유효한 단축이다.

## 6. 판정과 미달 시 대응

| 항목 | 목표 | 완화 |
|---|---|---|
| 4인 야외 프레임 | 60fps / 최저 30 | **불가** |
| 100분 힙 | 누수 0 | **불가** |
| 초기 다운로드 | ≤ 120MB | 가능 |
| 콜드 스타트 | ≤ 90초 | 가능 |

미달 시 배포 타깃을 바꾸지 않는다. **스코프를 깎되 순서가 정해져 있다**(19.0).

| 순위 | 깎는 것 | 이 문서에서 대응하는 지점 |
|---:|---|---|
| 1 | 파티클 예산 · 후처리 단계 | §3.2 파티클 960 → 축소, Volume 단계 축소 |
| 2 | 야외 맵 축소 · 시야 거리 단축 | §3.1 훈련 맵 프록시 200,000 → 축소 |
| 3 | 배경 NPC 제거 | §1 NPC 16,000 제거 |
| 4 | 4인 → 3인 + NPC (**최후 수단**) | §3.3 동시 캐릭터 스윕이 이 판단의 근거가 된다 |

순위를 미리 정해둔 이유는 기획서가 적은 그대로다 — 성능 문제가 터진 뒤에 급하게 정하면
가장 깎기 쉬운 것(인원)부터 깎게 되고, 4보직 1:1 대응에서 인원을 줄이면 곧 보직이 사라진다.

## 7. 지금 할 수 있는 것 / 에디터가 필요한 것

| 지금 | 에디터 필요 |
|---|---|
| 프록시 생성 스크립트 (에디터 스크립트) | 씬 저장 · 프리팹 |
| 더미 4인 접속 하니스 | WebGL 빌드 |
| 힙 기록 수집 스크립트 | Profiler 연결 · 실측 |

프록시는 코드로 만드는 것이 낫다 — 수치를 바꿔가며 스윕해야 하므로 손으로 배치한 씬보다
스크립트가 맞다. `M0_Synthetic`은 빈 씬 + 부트스트랩 컴포넌트 하나로 성립한다.
